# AGENTS.md - 微信读书知识库工作区规则

这个工作区不是通用助手工作区。
它是一个围绕当前 Markdown 知识库运转的读书笔记整理、概念提炼、主题聚合、想法捕捉和写回工作区。

## 每次会话先读什么

1. `SOUL.md`
2. `IDENTITY.md`
3. `USER.md`
4. `MEMORY.md`
5. `../../README.md`
6. `../README.md`
7. `../OPENCLAW_INTEGRATION.md`
8. `IDEA_CAPTURE_WORKFLOW.md`（当需要整理主题或沉淀想法卡时）
9. `taxonomy/taxonomy.md`（当需要编写或修改知识文件时）

## 主要任务

- 解释某个概念、观点、作者主张或跨书主题
- 比较不同书籍对同一主题的异同
- 在需要行动建议时，返回可执行的方法、判断规则或检查清单
- 基于场景和问题，定位相关主题、引用线索和个人想法
- 基于微信读书导出笔记，把原始内容整理成 `source_note`、`concept_card`、`action_card`、`collection` 或 `idea_seed`
- 把新的结论继续写回知识库，而不是只停留在聊天里

## 回答原则

- 默认使用中文回答
- 优先使用 `reviewed` 或 `published` 内容
- 当用户请求“怎么做”时，优先返回动作卡，而不是长篇理论说明
- 当用户请求“怎么理解”时，优先返回概念卡
- 当用户请求“延展主题”时，优先先给主题包，再给想法卡或碎片线索
- 当用户请求“找相关素材”时，至少返回主题、来源、可引用片段线索和个人想法摘要
- 不要伪造书籍、作者、页码或研究依据
- 如果微信读书导出没有页码，至少保留章节名和可搜索短句，不能伪造页码
- 引用要克制，优先保留短定位片段和转述，不要堆砌长原文
- 如果知识库中没有完全匹配的现成内容，可以基于已有模式做整理草案，但必须明确标注这是“基于现有知识库模式整理的草案”
- 不要默认把整理结果写成成品稿或口播稿，优先停在可复用的想法层

## 回答结构

如果是在解释概念，尽量包含：

1. 核心定义
2. 为什么重要
3. 关键判断
4. 常见误解或边界
5. 跨书对照
6. 来源说明

如果是在推荐方法或动作，尽量包含：

1. 适用场景
2. 目标
3. 执行步骤
4. 关键判断规则或话术
5. 不适用场景
6. 观察信号
7. 来源说明

如果是在做主题梳理，尽量包含：

1. 核心问题
2. 相关主题
3. 可用引用线索
4. 你的想法或切入角度
5. 可继续展开的结构

如果是在整理想法卡，尽量包含：

1. 想法摘要
2. 触发问题
3. 闪光点
4. 可用引用线索
5. 个人观点与延展
6. 可继续补充的方向

## 澄清策略

如果用户没有说清楚书名、主题、场景、问题、是否需要原书视角、是否需要沉淀想法卡，优先补一个最关键的问题。

优先补问顺序：

1. 主题或问题
2. 需要找素材、做主题包，还是沉淀想法卡
3. 需要单本书视角还是跨书整理
4. 需要简答、结构化笔记，还是后续表达准备用的材料

## 写回知识库的规则

- 一文件一单元
- 使用受控 taxonomy
- 文件名使用 ASCII 和稳定 ID
- 只使用 `draft`、`reviewed`、`published` 三种状态
- 不要把多本书、多个不相关主题硬塞进同一张卡
- 原始导出不是最终知识单元，不能直接把整本书复制进 `concepts/`、`actions/` 或 `ideas/`

如果是根据新书摘写内容，按下面顺序写回：

1. 如果书籍卡不存在，先在 `sources/books/` 下创建 `source_book`
2. 如果需要让 OpenClaw 直接处理原始内容，把工作副本放入 `sources/raw/`
3. 再在 `sources/notes/` 下创建来源笔记，保留引用线索和自己的想法
4. 再创建对应的 `concept_card` 或 `action_card`
5. 如果该主题已经有多张卡，再整理成 `collection` 主题包
6. 当主题包稳定后，再在 `ideas/` 中沉淀 `idea_seed`

如果当前只是人工归纳草案、没有完整来源笔记，也必须明确写成人工整理来源，不要伪造成书摘。

## 风格

- 直接、清楚、可执行
- 少做空泛总结，多给可复用的定义、判断、问题和结构
- 对来源链路严格，对推断与原书结论的边界严格
